React state "living too high" (lifted too high in the component tree) causes unnecessary re-renders, prop drilling, and performance bottlenecks. To fix this, move state to the lowest common ancestor, use useReducer for complex logic, or utilize context/state libraries for truly global data. 

Key Strategies to Lower React State:

Move State Down: If a piece of state is only used by a small branch of the component tree, move it down into those specific components rather than keeping it in a parent component.
Colocate State: Keep state as close to where it is used as possible. This limits the scope of re-renders.
Use useReducer: For complex state logic involving multiple sub-values, replace useState with useReducer to simplify management and optimize updates.
Use Refs (useRef): If data changes but does not need to trigger a re-render (like timer IDs or DOM references), use useRef instead of useState.
Derive State: Do not store data that can be calculated from props or other state variables. Calculate it on the fly, optionally wrapping expensive calculations in useMemo.
Context API: For truly global state (e.g., theme, user auth) that needs to be accessed by many distant components, use the Context API to avoid passing props through intermediate components. 
Signs State is Too High:

Prop Drilling: Passing props through intermediate components that do not need them.
Unnecessary Re-renders: Large parts of the application re-render when only a small piece of data changes.
Component Bloat: Parent components become hard to read and maintain due to excessive state logic. 
Lifting State Up

There should be a single “source of truth” for any data that changes in a React application. Usually, the state is first added to the component that needs it for rendering. Then, if other components also need it, you can lift it up to their closest common ancestor. Instead of trying to sync the state between different components, you should rely on the top-down data flow.

ES Modules and Non-tree-shakable Libraries

The problem here is that we have different module formats in JavaScript: ESM, CJS, AMD, UMD. "Module" is a single reusable piece of code that can be loaded into another piece of code.

 

When you see import { bla } from "bla-bla" or export const bla or export { bla } - it's ESM format.

Modern bundles can easily tree-shake ESM format, as we've seen already while experimenting with tree-shaking in our own code. Everything else that is not ESM is very hard to tree-shake.

 

You can check whether a library is ESM or not with a tiny is-esm npm package. It's a CLI tool that gives you a Yes/No answer. If Yes, it's ESM and it will be tree-shaken.

export default defineConfig({
  plugins: [react()],
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom"], // Separate React into its own chunk
        },
      },
    },
  },
});

 

This configuration ensures that commonly used libraries like React are grouped into a separate vendor chunk, optimizing caching.
